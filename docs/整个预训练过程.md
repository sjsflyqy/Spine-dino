### 一、Baseline框架与模型权重选择
#### 1.模型框架
Dinov2 & Dinov3自监督框架

#### 2.模型权重（简介）：
有其他可用权重，但截至 **2026年7月**，我没有查到一个像 RAD-DINO 那样成熟、公开、专门针对X线训练的 **DINOv3 checkpoint**。目前最现实的选择不是直接上超大DINOv3，而是：

> **DINOv3 ViT-B自然图像权重 + 你的脊柱X线继续预训练**，同时保留 **RAD-DINO-MAIRA-2** 作为医学域初始化和强基线。
>

##### 一、参数量
| 模型 | 参数量 |
| --- | ---: |
| DINOv2 ViT-S/14 | 21M |
| DINOv2 ViT-B/14 | 86M |
| DINOv2 ViT-L/14 | 300M |
| DINOv2 ViT-g/14 | 1.1B |


| 模型 | 参数量 | 中文数量级 |
| --- | ---: | ---: |
| DINOv3 ViT-S/16 | 21M | 2100万 |
| DINOv3 ViT-S+/16 | 29M | 2900万 |
| DINOv3 ViT-B/16 | 86M | 8600万 |
| DINOv3 ViT-L/16 | 300M | 3亿 |
| DINOv3 ViT-H+/16 | 840M | 8.4亿 |
| DINOv3 ViT-7B/16 | 6.716B | **约67亿** |


同样输入224×224时，DINOv3使用16×16 patch，对应196个图像patch；DINOv2/14对应256个patch。单看token数量，DINOv3-B并不一定比DINOv2-B更占显存。真正增加训练开销的是多裁剪、teacher-student、masked patch objective、Gram anchoring以及高分辨率训练。([Hugging Face](https://huggingface.co/facebook/dinov3-vitb16-pretrain-lvd1689m))

##### 二、目前可以用的X线DINO权重
###### 1. RAD-DINO-MAIRA-2
RAD-DINO的扩展版本，仍然是 **DINOv2 ViT-B/14，86.6M参数**，但预训练数据从RAD-DINO公开版本的882,775张胸片扩大到 **1,404,383张胸片**，包括五个公开数据集和一个私有数据集。权重已经公开在Hugging Face，可以直接通过Transformers加载。([Hugging Face](https://huggingface.co/microsoft/rad-dino-maira-2))

与原始RAD-DINO相比：

| 项目 | RAD-DINO | RAD-DINO-MAIRA-2 |
| --- | ---: | ---: |
| Backbone | DINOv2-B/14 | DINOv2-B/14 |
| 参数量 | 86.6M | 86.6M |
| 预训练X线 | 882,775 | 1,404,383 |
| 是否公开 | 是 | 是 |
| 是否兼容DINOv2 | 是 | 是 |
| 许可证 | MIT | MSRLA |


原始RAD-DINO公开模型使用了5个胸片数据集，MAIRA-2版本额外增加了约52万张私有胸片，因此是你现有RAD-DINO初始化最容易替换的升级版本。([Hugging Face](https://huggingface.co/microsoft/rad-dino))

不过需要检查它是否像原始RAD-DINO一样公开了**完整的DINO训练head和可继续预训练格式checkpoint**。MAIRA-2模型卡主要提供backbone；原始RAD-DINO明确公开了兼容DINOv2代码的backbone、DINO head、训练配置和增强代码，因此原始RAD-DINO在“直接恢复DINOv2自监督训练”方面可能更方便。([Hugging Face](https://huggingface.co/microsoft/rad-dino))

对你的意义

你可以先做两条DINOv2初始化实验：

+ RAD-DINO初始化；
+ RAD-DINO-MAIRA-2初始化。

若MAIRA-2明显更好，就用它替代原来的RAD-DINO；若差别很小，就继续使用训练恢复流程更完整的RAD-DINO。

---

###### 2. RayDINO / XRay-DINO：更大的胸片DINO权重
这篇论文名称是 **RayDINO**，Meta官方DINOv2仓库里把公开backbone称为 **XRay-DINO**。它使用873,000张胸部X线进行自监督训练，并在分类、分割、报告生成等九类放射学任务上验证。([arXiv](https://arxiv.org/abs/2405.01469?utm_source=chatgpt.com))

官方加载名称是：

```python
xray_dino_vitl16
```

这意味着它采用 **ViT-L/16**，参数量大约300M，是RAD-DINO-B的约3.5倍。权重需要通过Meta页面申请，许可证为FAIR非商业研究许可证。([GitHub](https://github.com/facebookresearch/dinov2))

优势

+ 胸片领域知识比较充分；
+ 模型规模比RAD-DINO大；
+ dense feature和下游能力强；
+ 官方提供checkpoint。

缺点

+ 胸片和脊柱骨性X线仍有领域差异；
+ 300M参数，继续自监督训练开销明显更高；
+ 许可证比RAD-DINO严格；
+ 架构是ViT-L/16，不能直接作为DINOv3-B的权重初始化。

我的建议是把它作为**大模型上限基线**，而不是你的第一版主模型。

---

###### 3. DAX：骨科X线更相关，而且参数很小
**DINO Adapted to X-Ray，MICCAI 2025** 在632,000多张术中骨科X线图像上进行DINO预训练，公开了多个轻量checkpoint：([GitHub](https://github.com/JoshuaScheuplein/DAX))

| DAX模型 | 参数量 |
| --- | ---: |
| DAX-ViT-T | 5.5M |
| DAX-ViT-S | 21.7M |
| DAX-ResNet18 | 11.2M |
| DAX-ResNet50 | 23.5M |


它的优势是**骨科X线域比胸片更接近你的脊柱X线**，并且checkpoint完全公开、参数量小、Apache 2.0许可证。([MICCAI 2025 - Open Access](https://papers.miccai.org/miccai-2025/paper/0521_paper.pdf?utm_source=chatgpt.com))

但它基于原始DINO路线，不是DINOv2或DINOv3，而且数据主要是术中透视/骨科X线，成像分布与站立位脊柱X线不同。因此：

+ 适合做参数效率基线；
+ 适合验证“骨科域预训练是否优于胸片域预训练”；
+ 不适合直接作为你的DINOv3初始化。

---

###### 4. XR-0：理论上最适合你，但暂时没找到公开权重
XR-0使用DINOv2 ViT-B/14，在 **115万张多解剖部位X线**上预训练，数据覆盖胸部、脊柱、膝、足、骨盆等部位。它的架构约86M参数，和RAD-DINO一致，但预训练解剖范围明显更适合你的脊柱任务。([arXiv](https://arxiv.org/html/2509.12146v1))

如果它公开checkpoint，它可能是你最理想的DINOv2初始化之一，因为：

+ 包含脊柱X线；
+ 不是只在胸片上训练；
+ 参数量仍然只有86M；
+ 使用DINOv2 image-level和patch-level目标。

不过我目前只查到论文，没有找到作者公开的正式模型仓库或可下载checkpoint。现阶段不能把它当作一定可用的权重，可以联系作者询问。

---

##### 三、有没有DINOv3医学权重？
###### MedDINOv3有公开权重，但不适合直接当X线模型
目前公开的医学DINOv3权重中，比较完整的是：

```latex
ricklisz123/MedDINOv3-ViTB-16-CT-3M
```

它是 **DINOv3 ViT-B/16，约86M参数**，在387万张二维轴位CT切片上进行领域自适应预训练。模型卡明确说明，它主要用于CT分割，并不推荐未经适配直接用于其他模态。([Hugging Face](https://huggingface.co/ricklisz123/MedDINOv3-ViTB-16-CT-3M))

因此它存在两个问题：

1. 虽然也是二维图像输入，但CT轴位切片与投影X线成像机制不同；
2. 胸片RAD-DINO至少同属于投影X线，MedDINOv3的CT医学先验不一定比自然图像DINOv3更适合脊柱X线。

你可以把它加入预实验，但不建议把它作为主初始化：

+ DINOv3-B自然图像权重；
+ MedDINOv3 CT权重；
+ RAD-DINO-MAIRA-2胸片权重；

先冻结编码器，在你的关键点或编号数据上做linear probing。谁好再决定继续预训练起点。

---

##### 四、目前最合理的DINOv3路线
###### 主路线：DINOv3-B，不要直接上L/H+/7B
建议使用：

```latex
facebook/dinov3-vitb16-pretrain-lvd1689m
```

它只有约86M参数，与RAD-DINO基本相同，并不是一个超大模型。官方已经公开ViT-S、S+、B、L、H+和7B权重，ViT-B可以通过Hugging Face直接加载。([GitHub](https://github.com/facebookresearch/dinov3))

你的实验可设计成：

###### 初始化对照
1. DINOv2-B自然图像权重；
2. RAD-DINO；
3. RAD-DINO-MAIRA-2；
4. DINOv3-B自然图像权重；
5. MedDINOv3-B CT权重；
6. 你的Spine-DINOv3-B。

这样可以回答三个重要问题：

+ 新一代自然图像DINOv3是否优于旧DINOv2；
+ X线领域先验是否比模型代际更新更重要；
+ 你的脊柱继续预训练是否能弥补DINOv3缺少医学预训练的问题。

这组实验的论文价值比只比较“RAD-DINO和你的模型”高得多。

---

##### 五、不能直接把RAD-DINO权重载入DINOv3
RAD-DINO是DINOv2-B/14，而DINOv3-B是ViT-B/16。二者至少存在这些差异：

+ patch embedding卷积核：14×14和16×16；
+ patch网格和位置编码不同；
+ register token和训练结构不同；
+ DINOv3加入新的训练阶段和目标；
+ checkpoint参数命名和部分模块不同。

因此不能像你之前把RAD-DINO加载进DINOv2那样，直接使用：

```python
model.load_state_dict(rad_dino_weights, strict=True)
```

最稳的DINOv3方法仍然是：

> 官方DINOv3-B自然图像权重初始化 → 在你的4万张脊柱X线上做领域自适应继续预训练。
>

---

##### 六、一个可能有研究价值的折中方案
你不一定要放弃RAD-DINO已经学到的X线知识。可以把它变成teacher：

+ **Student**：官方DINOv3-B初始化；
+ **Medical teacher**：冻结RAD-DINO-MAIRA-2；
+ **Generic teacher**：冻结原始DINOv3-B；
+ 使用你的无标注脊柱X线，让student同时对齐：
    - DINOv3的通用语义特征；
    - RAD-DINO的X线医学特征；
    - 你设计的脊柱结构自监督目标。

由于RAD-DINO和DINOv3-B的隐藏维度都是768，可以用投影层对齐CLS特征；patch网格不同，则将patch feature map插值到相同尺寸后蒸馏。

这比尝试强行加载不兼容的权重更合理，也可能形成一个创新点：

> **Cross-generation medical knowledge transfer from DINOv2 to DINOv3**
>

但第一步不要直接把方法做这么复杂。先完成三个初始化的冻结评估：

1. DINOv3-B；
2. RAD-DINO；
3. RAD-DINO-MAIRA-2。

通过结果再决定是否需要跨模型蒸馏。

---

##### 最终建议
你现在优先做这三件事：

1. 下载并测试 **RAD-DINO-MAIRA-2**，看它能否替换当前RAD-DINO。
2. 下载 **DINOv3 ViT-B/16**，不要使用ViT-L/H+/7B。
3. 在同一关键点和椎体编号任务上，先做冻结编码器快速比较：
    - RAD-DINO；
    - RAD-DINO-MAIRA-2；
    - DINOv3-B；
    - 可选MedDINOv3。

如果DINOv3-B已经接近或超过RAD-DINO，就直接以DINOv3-B继续做脊柱自监督预训练。如果DINOv3-B明显落后RAD-DINO，则说明X线领域先验仍然很重要，可以考虑“RAD-DINO teacher → DINOv3 student”的蒸馏路线。



#### 3.模型权重下载
dinov2系列三个没问题，但是dinov3中国拒绝下载，和SAM3一样都拒绝。

最终选择：<font style="background-color:#FBDE28;">rad-dino</font>、<font style="background-color:#FBDE28;">rad-dino-maira-2</font>、<font style="background-color:#FBDE28;">dinov2_vitb(无register)</font>、<font style="background-color:#FBDE28;">dinov3_vitb</font>。其中dinov2_vitb两个版本区别仅在于后者增加了 4 个 register tokens。DINOv2 官方说明，register 版本会在 patch embedding 后加入 4 个额外的可学习 token。  RAD-DINO 和 RAD-DINO-MAIRA-2 的公开配置都是：

```plain
architecture: Dinov2Model
hidden_size: 768
num_hidden_layers: 12
num_attention_heads: 12
patch_size: 14
```

并且配置中没有 register token 参数，因此<font style="background-color:#FBDE28;">它们对应标准的无-register DINOv2 ViT-B/14</font>。

```plain
同一患者 AP + LAT
        ↓
同一个冻结预训练骨干分别提取特征
        ↓
AP/LAT 特征进行线性拼接
        ↓
两个独立的 1×1 Conv 线性头
        ↓
同时输出 AP 和 LAT 的关键点
```

可以表示为：

```plain
F_ap  = frozen_backbone(ap_image)
F_lat = frozen_backbone(lat_image)

pred_ap  = linear_head_ap(concat(F_ap, F_lat))
pred_lat = linear_head_lat(concat(F_lat, F_ap))
```

这里：

+ `frozen_backbone` 完全冻结并保持 `eval()`。
+ `concat` 没有参数。
+ `linear_head_ap/lat` 只能是单层 `1×1 Conv`。
+ 不使用 ReLU、BatchNorm、多层卷积或 Transformer 融合。
+ 虽然输入了两个视图，但从冻结特征到输出仍是线性映射，因此仍属于线性探测。

###### 1.2.1 输出形式
建议保留论文的 CenterNet 式定义，而不是直接用全连接层回归 136 个坐标：

每个视图输出：

+ `hm`：1 通道椎体中心热图
+ `reg`：2 通道中心点偏移
+ `wh`：8 通道，表示四个角点相对中心的偏移

即每个视图的线性头只需要输出 11 个通道：

```plain
1 hm + 2 reg + 8 corner offsets = 11
```

在热图中取 17 个椎体中心，按纵向排序对应 T1–L5，再恢复每个椎体的四角点，最终得到每个视图的 68 个关键点。

训练损失仍可按照论文使用：

+ 中心热图 focal loss
+ 中心偏移 L1 loss
+ 角点偏移 L1 loss

损失函数是非线性的并不影响“线性探测”的定义；关键在于从冻结特征到预测结果只有一个可训练线性层。

###### 1.2.2 是否也要做单图输入
任务 7 可以额外提供单视图消融实验：

+ LAT-only
+ AP+LAT paired

但论文对齐的主要结果应采用 AP+LAT 成对输入。四个预训练模型都使用完全相同的双视图线性头。

###### 2.2.1 不建议直接坐标全连接回归
“输入单图直接输出 44 个坐标”技术上可以，例如：

```plain

```

+ CLS/global pooling 会丢失精细空间信息。
+ 医学关键点对几个像素的偏差都很敏感。
+ RAD-DINO、DINOv2、DINOv3 的 patch token 更适合生成空间热图。
+ 论文也是中心热图加偏移，而不是简单全连接坐标回归。

##### 2.3 线性探测指标（收敛结果）
**<font style="background-color:#FBDE28;">选择验证集 </font>**`**<font style="background-color:#FBDE28;">MRE_mm</font>**`**<font style="background-color:#FBDE28;"> 最低的轮次。  </font>**

任务 8 对应胡婷婷的 LSLD-Net 论文：

+ `MAE`：关键点坐标的平均 L1 距离。
+ `MRE`：关键点坐标的平均欧氏距离。
+ `SDR@2/3/4/5 mm`：欧氏误差不超过相应阈值的关键点比例。
+ 按论文采用 `0.143 mm/pixel` 将像素误差换算成毫米。

当前指标如何计算

对每个关键点，先将归一化坐标误差恢复为原图像素误差，再乘论文使用的像素间距 `0.143 mm/pixel`：

```plain
Δx_mm = (x预测 - x真实) × 原图宽度 × 0.143
Δy_mm = (y预测 - y真实) × 原图高度 × 0.143
```

然后计算：

```plain
MAE = mean(|Δx_mm| + |Δy_mm|)

MRE = mean(sqrt(Δx_mm² + Δy_mm²))

SDR@δ = 100 × 径向误差不超过δ的关键点数 / 全部关键点数
```

##### 1.3 每一个选项的作用
`CUDA_VISIBLE_DEVICES=0,1`

指定这个任务只能看到物理 GPU 0 和 1。脚本内部会把它们编号为本任务的 GPU 0、1。并行任务必须使用互不重叠的 GPU 编号。

`--pretrained-weights`

训练初始化权重。DINOv2、RAD-DINO、MAIRA-2 的网络结构都是 ViT-B/14，区别主要是初始化权重。DINOv3 使用 ViT-B/16 对应的转换后训练初始化权重。

`--output-dir`

日志、恢复 checkpoint、teacher 权重和运行计划的保存目录。

+ 独立实验必须使用不同目录。
+ 10→20→50→100 passes 续训时必须使用同一个目录。
+ 不建议复用原先短训练的目录，因为原来的调度长度和保存逻辑不同。

`--ngpu 2`

启动两个分布式训练进程，每张可见 GPU 对应一个进程。它必须和 `CUDA_VISIBLE_DEVICES` 中的 GPU 数量一致。

`--batch-size 4`

每张 GPU 的 batch size，不是总 batch。

双卡时：

```plain
全局 batch = 2 × 4 = 8
```

提高 batch size 可能提高 GPU 利用率，但同时增加显存、系统内存中的预取数据和单步计算量。建议先保持 4。

`--num-workers 4`

每个 GPU 训练进程的数据加载进程数。双卡时总 worker 数是：

```plain
2 × 4 = 8
```

它不是整个任务一共 4 个。共享服务器上不建议直接设成 8 或更高。

`--prefetch-factor 1`

每个 DataLoader worker 提前准备多少个 batch。内存紧张时设为 1 最稳妥。

`--epoch-length 200`

代码内部一个“伪 epoch”固定包含 200 个训练 step。它主要用于学习率调度和日志，并不等于完整遍历一次 60,570 张图。

一般不要修改这个值。

`--target-passes 10`

这一次运行训练到多少次等效数据遍历后停止。

双卡、全局 batch 8 时，程序已经验证：

```plain
10 passes = ceil(60570 × 10 / 8)
          = 75,713 steps
```

`--schedule-passes 100`

学习率、weight decay 和 teacher EMA 调度的最终规划长度。

这里设置为 100，是因为你提出后面可能训练到 100 passes。第一次虽然只跑到 10 passes，但使用的是完整 100-pass 调度的前 10%。

后续续训时这个值必须保持为 100。

`--checkpoint-period 10000`

每 10,000 steps 保存一次完整恢复 checkpoint。恢复 checkpoint 包含学生、教师、优化器等状态，主要用于断点续训，不是下游模型权重。

`--checkpoint-max-to-keep 2`

只保留最近的两个完整恢复 checkpoint，避免中间权重不断累积。

`--checkpoint-keep-every 0`

仅 DINOv3 使用。关闭永久保留某些历史 checkpoint 的机制，否则即使设置 `max-to-keep`，带 `_keep` 的目录仍可能长期占用磁盘。

`--teacher-period 0`

不定期保存中间 teacher，只在当前训练阶段结束时保存一次合并后的 EMA teacher 权重。下游线性探测通常使用这个阶段末 teacher。

`--global-crop-size`

DINO teacher/student 的两个大视野裁剪边长：

+ DINOv2/RAD-DINO/MAIRA-2：518
+ DINOv3：512

这是因为它们分别对应 patch size 14 和 patch size 16。

`--local-crop-size`

多个局部裁剪的边长：

+ DINOv2 系列：196
+ DINOv3：192

`--global-crop-scale 0.50 1.00`

全局裁剪占原图面积的比例范围，即随机选择原图约 50%～100% 的区域。

`--local-crop-scale 0.20 0.50`

局部裁剪占原图面积的比例范围，即随机选择约 20%～50% 的区域。

`--local-crops-number 8`

每张原图生成 8 个局部视图。加上两个全局视图，一张原图总共会产生 10 个训练视图。这也是数据加载内存明显高于普通分类训练的原因之一。

##### 1.4 epoch、pass 和后续增加训练量
你的原命令：

```plain
100 epochs × 200 steps × batch 4
= 80,000 张图
```

这是单卡情况。数据集有 60,570 张图，因此只相当于：

```plain
80,000 / 60,570 ≈ 1.32 passes
```

如果是双卡、每卡 batch 4：

```plain
100 epochs × 200 steps × 8
= 160,000 张图
≈ 2.64 passes
```

所以“100 epochs”和“100 passes”完全不是一回事。

如果你只是想训练代码意义上的 100 个 epoch，可以使用：

```plain
--epochs 100
```

并且不传 `--target-passes`、`--schedule-passes`。但这种方式不适合分阶段长期训练，因为后续修改总 epoch 数会重新生成学习率调度，恢复时可能发生学习率不连续。

建议继续使用 pass 方式。

训练完 10 passes 后，训练到 20 passes：

```plain
# 保持其余所有参数和 output-dir 不变
--target-passes 20 \
--schedule-passes 100
```

然后训练到 50：

```plain
--target-passes 50 \
--schedule-passes 100
```

最后训练到 100：

```plain
--target-passes 100 \
--schedule-passes 100
```

程序会自动从同一输出目录的最近 checkpoint 恢复，不会重新训练前面的部分。

如果未来可能超过 100 passes，例如到 200，那么最好现在就将：

```plain
--schedule-passes 200
```

之后始终保持 200。若已经按 `schedule-passes 100` 完成了 100 passes，再直接改成 200，会改变既定的学习率曲线，不再是严格连续的同一次训练计划。

##### 1.6 保存的checkpoint解释
rank0 和 rank1 分别是什么

你的命令是：

```plain
CUDA_VISIBLE_DEVICES=4,5
--ngpu 2
```

对应关系为：

```plain
rank 0 → CUDA_VISIBLE_DEVICES 中第一张卡 → 物理 GPU 4
rank 1 → CUDA_VISIBLE_DEVICES 中第二张卡 → 物理 GPU 5
```

当前恢复点是：

```plain
model_0059999.rank_0.pth
model_0059999.rank_1.pth
```

它们不是两个独立模型，也不是：

```plain
rank0 = student
rank1 = teacher
```

而是同一个完整训练状态的两个 FSDP 分片。每份文件都包含：

+ student 模型的一部分参数；
+ teacher/EMA 模型的一部分参数；
+ 优化器状态的一部分；
+ 当前 iteration 等恢复信息。

双卡 FSDP 将模型、梯度和优化器状态分散到两个训练进程，因此需要分别保存。恢复时必须同时具备同一步的 rank0 和 rank1 文件。

```plain
rank0 shard + rank1 shard
            ↓
一个完整的双卡训练状态
```

不能只拿 `rank_0.pth` 做下游任务，也不能只保留其中一个。下游最终应该使用阶段结束时合并生成的：

```plain
eval/training_75712/teacher_checkpoint.pth
```

##### 1.7 dinov2和dinov3显存差异原因
主要原因不是模型参数量差很多，而是 token 数量、FSDP 实现和显存统计口径不同。当前状态是正常的，并不代表 DINOv2 真有 17GB 的有效张量一直在使用。

###### 实际日志对比
当前 DINOv2 两个 rank 的日志都显示：

```plain
max mem ≈ 7,707MB
```

DINOv3 日志显示：

```plain
max mem ≈ 7,492MB
```

也就是说，PyTorch 实际训练张量的峰值只相差约：

```plain
7707 - 7492 = 215MB
```

但 `nvidia-smi` 显示：

```plain
DINOv2：
GPU 4：14,330MB
GPU 5：17,110MB

DINOv3：
GPU 6：9,394MB
GPU 7：9,388MB
```

这里差出来的大部分是“CUDA 已保留显存”，而不是当前仍被张量占用的显存。

###### `nvidia-smi` 为什么比日志大很多
训练日志中的 `max mem` 主要对应：

```plain
torch.cuda.max_memory_allocated()
```

它统计实际张量分配峰值。

`nvidia-smi` 还会统计：

+ PyTorch CUDA 缓存池保留的显存；
+ FSDP all-gather/reduce-scatter 通信缓冲区；
+ NCCL 通信缓冲区；
+ cuBLAS、attention 等算子工作区；
+ CUDA context；
+ 已经释放给 PyTorch allocator、但尚未归还显卡驱动的显存。

所以对 DINOv2 来说，当前大致是：

```plain
有效张量峰值：约7.7GB
nvidia-smi占用：14～17GB
额外部分：缓存、通信缓冲和算子工作区
```

这些缓存后续可以重复利用，因此不一定是内存泄漏。

###### DINOv2 的 token 数量更大
虽然输入图像尺寸非常接近，但两个模型的 patch size 不同。

DINOv2：

```plain
global：518 / 14 = 37
global tokens：37 × 37 = 1369

local：196 / 14 = 14
local tokens：14 × 14 = 196
```

DINOv3：

```plain
global：512 / 16 = 32
global tokens：32 × 32 = 1024

local：192 / 16 = 12
local tokens：12 × 12 = 144
```

因此 DINOv2 的全局 token 数多约34%：

```plain
1369 / 1024 ≈ 1.34
```

而标准 attention 中间矩阵大致随 token 数平方增长：

```plain
1369² / 1024² ≈ 1.79
```

也就是说，全局 crop 的部分 attention 工作区可能比 DINOv3 大约79%。这会让 CUDA allocator 申请更大的临时显存块，并在后续保留这些缓存。

###### FSDP1 和 FSDP2 的区别
两边都配置了：

```plain
SHARD_GRAD_OP
每卡 batch size = 4
```

但底层实现不同：

+ DINOv2 使用较老的 FSDP1，并且手动 reshard teacher；
+ DINOv3 使用新的 composable FSDP2；
+ DINOv3 会对 student 和 EMA teacher 更精细地 reshard；
+ FSDP2 基于 DTensor 管理参数，通常显存布局和缓存碎片更可控；
+ DINOv2 FSDP1 的 all-gather 和手动 teacher reshard 更容易留下较大的 CUDA 缓存段。

这也是 DINOv2 的 `nvidia-smi` 占用明显高于其 `max_memory_allocated` 的重要原因。

###### 为什么 GPU 4 和 GPU 5 不一样
两张卡实际张量峰值基本一样：

```plain
rank 0：约7.68GB
rank 1：约7.71GB
```

因此计算和数据是均衡的。

`nvidia-smi` 的14.3GB和17.1GB差异，更可能来自：

+ 查询时一个 rank 正在进行 all-gather；
+ CUDA allocator 在两个 rank 上保留了不同尺寸的显存块；
+ NCCL 缓冲区建立时间不同；
+ attention/cuBLAS 工作区选择不同；
+ 显存碎片差异。

如果这个差异后续保持稳定，但训练正常、日志 `max mem` 不持续增长，就不属于内存泄漏。

真正需要警惕的是：

```plain
nvidia-smi显存每隔一段时间持续上涨
例如 14GB → 16GB → 18GB → 20GB → OOM
```

目前仅从日志看，没有这种迹象。

###### FP16 和 BF16 不是主要原因
当前配置：

```plain
DINOv2：FP16
DINOv3：BF16
```

FP16 和 BF16 都是每个元素2字节，所以不能解释几GB的差距。FP16 的 GradScaler 只会产生很小的额外开销。

###### 是否需要降低显存
目前不需要调整。DINOv2 已经稳定训练，并且速度非常快：

```plain
DINOv2：约0.30～0.34秒/step
DINOv3：约0.50～0.65秒/step
```

DINOv2 虽然在 `nvidia-smi` 中保留了更多显存，但训练吞吐比 DINOv3 更高。只要每张卡总显存足够，并且不打算在 GPU 4、5 上再放其他任务，就可以继续运行。

不建议训练中途改 batch size，因为会改变全局 batch 和既定的 100-pass 调度计划。也不要在训练循环中频繁调用 `torch.cuda.empty_cache()`，它可能降低速度。

目前可以判断：

+ DINOv2 双卡分片修复已生效；
+ 两个 rank 的真实张量显存基本平衡；
+ 14～17GB主要包含 PyTorch/CUDA保留显存；
+ 没有发现显存泄漏证据；
+ 当前运行状态正常。

你当前配置已经有关键的抗坍塌机制：teacher EMA、teacher temperature warm-up、centering / Sinkhorn、DINO + iBOT 目标、梯度裁剪和最后层短暂冻结。因此建议第一轮不要先改算法，而是做一个小规模试跑：

+ 用随机初始化跑 5–10 passes，确认没有 NaN/Inf。
+ 观察 teacher 输出的熵或 prototype 使用情况：若快速变成极低熵、只剩极少 prototype 被使用，才是典型坍塌信号。
+ 先做一次线性探测；仅看 SSL loss 下降不能证明学到了有用表征。
+ 若不稳定，优先降低学习率、延长 warm-up、提高 teacher 初始 EMA momentum（如 `0.996–0.998`），不要随意降低 teacher temperature。
+ 若稳定但效果弱，优先增加训练 passes、增强数据多样性，或先用 ViT-S/14 做随机初始化可行性验证；小数据直接从头训练 ViT-B 的性价比通常不高。

###### 在哪里修改训练参数
配置中的这一部分控制训练：

```plain
training:
  batch_size: 4
  epochs: 100
  learning_rate: 0.001
  weight_decay: 0.0
  workers: 4
  seed: 42
  early_stopping:
    enabled: true
    patience: 20
    min_delta: 0.01
```

对应关系：

+ `epochs`：最大训练轮数
+ `batch_size`：batch大小
+ `learning_rate`：学习率
+ `weight_decay`：权重衰减
+ `workers`：DataLoader进程数
+ `seed`：随机种子
+ `enabled`：是否开启早停
+ `patience`：连续多少轮不改善后停止
+ `min_delta`：达到多大变化才算有效改善

例如想最多训练200轮、30轮不改善再停止：

```plain
training:
  epochs: 200
  early_stopping:
    enabled: true
    patience: 30
    min_delta: 0.01
```

想关闭早停：

```plain
early_stopping:
  enabled: false
  patience: 20
  min_delta: 0.01
```

这时会完整训练 `epochs` 指定的轮数。
